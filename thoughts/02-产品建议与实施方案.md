> 日期: 2026-04-19
> 前置: 01-产品哲学审视与PKM理论基石.md
> 基于完整代码审阅后制定，每条建议对应具体的代码层和文件

## 短期方案（1-2 周可落地）

### 方案一：笔记鲜活度仪表板

**理论依据**: 扩展心智论题 -- 工具应主动反映知识状态，而非被动等待查询。Matuschak 的"常青笔记持续修订"需要可视化提醒。

**当前代码现状**:
- `wiki-view.ts` 的 `renderIndex()` 已有 `extractUpdated()` 提取更新时间
- frontmatter 中有 `last_updated` 和 `status` 字段
- stats 区域（L268-272）展示概念/实体/来源数量

**实施方案**:
1. 在 `wiki-view.ts` 的 stats 区域新增"知识健康度"指标：
   - `staleness`: 核心概念中 last_updated 超过 30 天的比例
   - `linkDensity`: 平均每页的双链数量
   - `orphanRisk`: 链接数 < 2 的页面比例
2. 新增 `src/core/health.ts` 模块，提供 `computeWikiHealth(wikiPages)` 函数
3. 在 Wiki View 首页的 stats bar 下方展示一个简洁的健康度条（绿/黄/红）
4. 点击健康度条可展开"需要关注的页面"列表，按 staleness 排序

**涉及文件**: `src/views/wiki-view.ts`, 新增 `src/core/health.ts`

**设计原则**: 渐进式披露 -- 默认只显示一个颜色条，不增加视觉噪音

---

### 方案二：编译历史 diff

**理论依据**: "编译"隐喻的边界 -- 知识编译是概率性的，用户需要看到每次编译改变了什么。

**当前代码现状**:
- `compile.ts` 的 `buildCompileReport()` 已生成 `CompileReport`（含 newConcepts, modifiedConcepts, deletedConcepts）
- `CompileCache.pages` 记录了每个页面的 `generatedAt` 时间戳
- 但没有存储编译前后的内容 diff

**实施方案**:
1. 在 `CompileCache` 类型（`types.ts`）中新增字段：
   ```ts
   compileHistory: Array<{
     date: string;
     action: "full" | "incremental";
     added: string[];      // 新增的页面名
     modified: string[];   // 修改的页面名
     removed: string[];    // 删除的页面名
     conflicts: string[];  // 冲突页面名
   }>;
   ```
2. 在 `compile.ts` 的 `runCompile()` 末尾，将 report 信息追加到 `compileHistory`
3. 在 `compile-view.ts` 中新增"历史"标签页，展示最近的编译记录
4. 每条记录可展开查看具体变更的页面列表

**涉及文件**: `types.ts`, `src/core/compile.ts`, `src/views/compile-view.ts`

**设计原则**: 只记录元数据（页面名+变更类型），不存储内容 diff，避免缓存膨胀

### 方案三：LLM 置信度标注

**理论依据**: LLM 是编译器而非作者 -- 用户需要知道哪些"编译结果"需要重点审查。

**当前代码现状**:
- `compile-pages.ts` 的 `buildConceptPrompt()` 已经要求 LLM 标注 `[原创]`
- frontmatter 中有 `status: "draft"` 表示未审查
- 但没有对 LLM 生成内容的可靠性进行分层

**实施方案**:
1. 在 `wiki-schema.ts` 的 `buildPageRules()` 中新增规则：
   - 概念定义（第一行）标注为"核心内容"
   - 从 raw 素材直接提取的段落标注来源文件
   - LLM 自行推断的连接和分析标注为 `[推断]`
2. 在 frontmatter 中新增可选字段 `confidence: "high" | "medium" | "low"`
   - 如果页面完全基于用户原创笔记（`original` 字段非空）→ high
   - 如果页面完全基于外部素材（仅 `reference`）→ medium
   - 如果页面包含 synthesis 的推断内容 → low
3. 在 `wiki-view.ts` 的页面卡片中，用不同色调展示置信度

**涉及文件**: `src/core/wiki-schema.ts`, `src/core/compile-pages.ts`, `src/views/wiki-view.ts`

**设计原则**: 置信度由素材来源自动推断，不需要 LLM 额外判断

---

### 方案四：语义化链接关系

**理论依据**: 双向链接研究 -- 链接应携带语义信息，而非仅表示"相关"。

**当前代码现状**:
- 所有双链使用 `[[PageName|Display]]` 格式，无语义区分
- `findBacklinks()` 只检查链接是否存在，不区分关系类型
- prompt 中要求"至少链接 3 个现有概念"，但不区分链接的语义

**实施方案**:
1. 在 prompt 模板中引入语义化链接语法：
   ```
   [[ConceptName|显示名]] -- 支持当前观点
   [[ConceptName|显示名]] -- 提供反例
   [[ConceptName|显示名]] -- 延伸讨论
   [[ConceptName|显示名]] -- 形成对比
   ```
2. 在 `wiki-shared.ts` 中新增 `extractLinkRelations()` 函数，解析语义标注
3. 在 `wiki-view.ts` 的反向链接区域，按关系类型分组展示（替代当前的平铺列表）
4. 在图谱视图 `wiki-mindmap.ts` 中，用不同线型表示不同关系

**涉及文件**: `src/core/wiki-schema.ts`, `src/views/wiki-shared.ts`, `src/views/wiki-view.ts`, `src/views/wiki-mindmap.ts`

**设计原则**: 语义标注是可选的，不影响现有的裸链接功能

## 中期方向（1-2 月）

### 方案五：知识反哺机制 -- Query 即积累

**理论依据**: Matuschak "knowledge work should accrete" + Karpathy 编译式知识库 -- 每次查询都应让知识库变得更好。

**当前代码现状**:
- `chat-view.ts` 的 `send()` 方法使用 `vectorSearch()` 检索相关页面
- 查询结果以 `chatHistory` 内存数组暂存，关闭面板后消失
- `wiki/` 下有 `syntheses/` 目录但只有编译时生成的综合分析

**实施方案**:
1. 在 `chat-view.ts` 的 `send()` 末尾，当 AI 回答质量较高时（用户未停止、回答长度 > 200 字），弹出一个轻量提示："将此对话保存为综合分析？"
2. 用户确认后，调用现有 `buildSynthesisPrompt()` 的逻辑，将对话提炼为 synthesis 页面
3. 自动写入 `wiki/syntheses/` 并更新 `index.md`
4. 在 `CompileCache` 中记录 query-derived 页面的来源对话摘要

**涉及文件**: `src/views/chat-view.ts`, `src/core/compile.ts`

**设计原则**: 主动建议而非自动执行，尊重用户控制权

### 方案六：本体演化引擎

**理论依据**: 知识图谱本体设计 -- 轻量本体胜过重量本体，分类应从使用中涌现。

**当前代码现状**:
- `templates.ts` 硬编码了三个层级：核心概念/方法框架/实践经验
- 用户可通过 `prompt-config.json` 自定义 levels
- 但没有机制检测实际使用中是否需要新增或合并层级

**实施方案**:
1. 在 lint 工作流中新增"本体健康检查"：
   - 检测每个 level 下的概念数量分布（如某 level 只有 1 个概念，可能分类过细）
   - 检测跨 level 的链接密度（如果两个 level 的概念高频互链，可能需要合并）
   - 检测概念命名冲突（不同 level 出现同名概念）
2. 在编译报告中新增"本体建议"区块：
   ```
   本体建议:
   - "实践经验" 下仅 1 个概念，考虑合并到 "方法框架"
   - "核心概念" 和 "方法框架" 之间有 15 条跨级链接，可能需要重新分类
   ```
3. 用户可在 `prompt-config.json` 中调整 levels，系统自动适配

**涉及文件**: 新增 `src/core/lint.ts`（或扩展现有逻辑）, `src/core/compile.ts`

**设计原则**: 只建议不自动执行，用户始终掌控知识结构

### 方案七：渐进式认知状态

**理论依据**: 数字花园理论 -- seedling/budding/evergreen 成熟度 + Gwern.net 确定性标注。

**当前代码现状**:
- frontmatter 中只有 `status: "draft" | "reviewed" | "outdated" | "conflict"`
- 这是二元状态：要么未审查，要么已审查
- 没有表达知识的成熟度和确定性

**实施方案**:
1. 将 status 扩展为双维度：
   ```yaml
   status: "seedling" | "budding" | "evergreen"  # 成熟度
   certainty: "speculative" | "probable" | "verified"  # 确定性
   ```
2. 映射关系：现有 `draft` → `seedling`，`reviewed` → `budding`
3. 自动晋升规则：
   - 被链接超过 5 次 → seedling → budding
   - 被链接超过 15 次且最近 90 天内修订过 → budding → evergreen
   - 包含 `[原创]` 标注 → certainty 提升
4. 在 Wiki View 页面卡片中用图标表示成熟度（种子/萌芽/常青树）

**涉及文件**: `types.ts`, `src/core/wiki-schema.ts`, `src/views/wiki-view.ts`

**设计原则**: 向后兼容 -- 旧的 `draft`/`reviewed` 状态在加载时自动映射

---

### 方案八：间隔式知识复习

**理论依据**: 间隔重复 + Matuschak "evergreen note maintenance approximates spaced repetition" -- 笔记修订是主动整合，比被动复习更有效。

**当前代码现状**:
- 没有任何复习或提醒机制
- `last_updated` 字段存在但未被主动使用

**实施方案**:
1. 在 `health.ts` 中新增 `getReviewCandidates(wikiPages)` 函数：
   - 核心概念 last_updated > 30 天 → 建议回访
   - 最近新增的 raw 素材中提及了某现有概念 → 建议整合新理解
   - 概念被频繁链接但内容较短 → 建议扩展
2. 在 Wiki View 首页新增"复习建议"区域（折叠式，不干扰主流程）
3. 每条建议是可点击的，直接导航到目标页面并高亮需要更新的区域

**涉及文件**: `src/core/health.ts`, `src/views/wiki-view.ts`

**设计原则**: 智能而非机械 -- 不是"该复习了"，而是"你的理解可能已经进化了"

## 长期愿景（3-6 月）

### 方案九：知识库作为交流伙伴

**理论依据**: Luhmann 的卡片盒作为"交流伙伴" -- 工具应能主动提问、质疑、建议连接。

**当前代码现状**:
- `chat-view.ts` 是被动问答模式：用户提问，AI 回答
- AI 的 system prompt 是静态的，不携带知识库的"意图"

**实施方案**:
1. 新增"主动对话"模式 -- 当用户打开 Chat View 时，AI 可以基于知识库状态主动发起话题：
   - "你最近写了关于 X 的笔记，它和你之前的 Y 理论似乎有张力，要不要展开讨论？"
   - "Z 这个概念已经被链接了 20 次但内容还很短，是否值得深化？"
2. 在 system prompt 中注入知识库的"状态摘要"：
   - 最近新增的概念、最近的冲突、需要复习的页面
3. AI 在回答中可以反问用户，推动知识的深化而非仅仅回答问题

**涉及文件**: `src/views/chat-view.ts`, `src/core/llm.ts`

---

### 方案十：认知卸载最大化

**理论依据**: 认知负荷理论 + 扩展心智论题 -- 将所有可自动化的信息管理任务交给系统。

**当前代码现状**:
- 用户需要手动触发编译、手动审查页面、手动标记 reviewed
- 分类、链接、摘要已由 LLM 自动完成

**实施方案**:
1. 自动编译已实现（Pro 功能），扩展为全自动管道：
   - raw 素材变更 → 自动编译 → 自动标记 confidence → 自动更新 index
   - 用户只需审查"低置信度"和"冲突"页面
2. 新增"智能静默"模式：
   - 当 LLM 对某个概念的重新编译结果与现有内容差异 < 10% 时，静默更新
   - 差异 > 10% 时弹出审查通知
3. 最终目标：用户只做三件事 -- 捕获素材、审查冲突、深化理解

**涉及文件**: `src/core/compile-pages.ts`, `src/main.ts`
